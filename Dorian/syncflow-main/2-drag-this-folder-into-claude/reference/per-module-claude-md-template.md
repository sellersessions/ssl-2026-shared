# Per-module `CLAUDE.md` template

> The contract for what `start-implementation` writes to `~/syncflow-projects/<brand>/modules/0N-<slug>/CLAUDE.md`. When the delegate `cd`s into that folder and runs `claude`, their Claude Code reads this file and knows exactly what it's working on. Read alongside `implementation-phase.md` Principle 3.

---

## Why this template exists

The delegate's machine probably has many other Claude Code projects with their own `CLAUDE.md` files: personal projects, side gigs, other brands. **We don't touch any of those.**

This template defines the per-module `CLAUDE.md` that lives at `modules/0N-<slug>/CLAUDE.md`. Folder = scope. When the delegate `cd`s in and runs `claude`, their CC reads this file. When they `cd` somewhere else, this file is invisible.

The CLAUDE.md generated from this template gives the delegate's CC enough context to:
- Know which module + brand it's working on
- Know the current phase + status *(from `status.json`)*
- Have the build plan + verification plan inlined
- Follow single-project hygiene rules
- Update `status.json` when phases pass verification
- Know when to hand back to syncflow *(in Cowork)*

## Current state *(check `status.json` at the start of every session)*

The single file you need to know: `status.json` at the root of this folder. It's where you report progress.

Initial shape *(written by syncflow at module kickoff)*:

```json
{
  "module_n": "{{module_n}}",
  "module_name": "{{module_name}}",
  "brand_slug": "{{brand_slug}}",
  "current_phase": 1,
  "phases": {
    "1": { "status": "in_progress", "started_at": "{{started_at}}", "verified_at": null, "notes": "" },
    "2": { "status": "pending", "started_at": null, "verified_at": null, "notes": "" },
    "3": { "status": "pending", "started_at": null, "verified_at": null, "notes": "" },
    "4": { "status": "pending", "started_at": null, "verified_at": null, "notes": "" },
    "5": { "status": "pending", "started_at": null, "verified_at": null, "notes": "" }
  },
  "deliverables_built": [],
  "blockers": [],
  "last_session": null,
  "next_action": "Read build-plan.md § Phase 1, run verification, update this file"
}
```

**At the start of every session:** read `status.json` first. Tell the delegate where they left off. Don't assume — read.

**At the end of a phase that passes verification:** update `status.json` to mark the phase `verified` with `verified_at` timestamp + a one-line note about what was built. Set `current_phase` to the next phase.

**At the end of a session:** write a one-line summary to `last_session` so the next session knows what just happened.

## Single-project hygiene *(non-negotiable)*

These rules come from the parent brand's stack. Do not violate them.

1. **Use the existing infrastructure** the delegate's stack has:
   - Supabase project: **{{supabase_project_name}}** — *(don't spawn new)*
   - n8n instance: **{{n8n_instance_url}}** — *(don't spawn new)*
   - GitHub repo for this brand: **{{github_repo}}** — *(don't spawn new)*
   - Vercel project: **{{vercel_project_name}}** — *(don't spawn new)*
   - ClickUp space: **{{clickup_space_id}}** — *(don't spawn new)*

   If you think you need a new one, **stop and ask the delegate.** New projects are never created silently.

2. **Credentials live in `../_shared/credentials/.env`** *(or the delegate's secret manager)*. Never ask the delegate for the same key twice. Never store secrets in code. Never commit `.env`.

3. **Schema-first** — Phase 1 always builds the data schema before any logic. *(See `simplicity-ladder.md` § rung discipline.)*

4. **Working local doesn't count** — Phase 5 always specifies cloud deployment + monitoring. If a phase only works on the delegate's laptop being open, it's not shipped *(Sim P5)*.

5. **The last 20% takes longer than the first 80%** — auth, hosting, alerts, rate limit handling, edge cases. Don't optimistically estimate Phase 5 *(Sim's "honest truths" lesson)*.

6. **Verification > speed.** No phase ships without its verification plan passing. If you're tempted to skip a check to ship faster, write the check anyway and run it.

## Hand-off protocol *(when to talk back to syncflow)*

You're a Claude Code instance executing a plan. Some things you don't decide alone — they go back to syncflow (the delegate's Cowork project) for sign-off:

| Trigger | What to do |
|---|---|
| Phase passes verification | Update `status.json`. Tell the delegate: *"Phase N verified. Bring this back to syncflow with `update Module {{module_n}} status to phase_N_complete` to record the milestone."* |
| You hit a blocker that requires a brain-level decision *(e.g. "should we use SQS or EventBridge?")* | Don't pick. Ask the delegate. They take it back to syncflow if needed. |
| The build plan is wrong / a phase needs reshape | Don't silently rewrite. Tell the delegate. They go back to syncflow and run `regenerate-section` or `swap-module`. |
| All 5 phases done | Update `status.json` to all-verified. Tell the delegate: *"Module {{module_n}} built v1. Take this to syncflow: 'Module {{module_n}} built'. They'll set status to `built_v1` and then prompt the deploy step."* |
| Module is deployed and running unattended | Tell the delegate to update syncflow: `update Module {{module_n}} status to deployed`. |

You are NOT the consultant. You are the builder. The consultant lives in Cowork.

## Versioning + idempotency

`start-implementation` is idempotent. If `modules/0N-<slug>/CLAUDE.md` already exists when the skill fires, it doesn't overwrite by default — it surfaces the existing file and asks the delegate if they want to refresh.

If they do want a refresh, the skill regenerates from this template using the current brain state. The previous CLAUDE.md is moved to `CLAUDE.md.bak.{{timestamp}}` for safety.

---

## Don't change the template structure without considering downstream

The headings + section order are stable. If you reshape the template, the downstream contract changes:
- Delegate's CC behaviour changes *(it reads sections in expected order)*
- `status.json` schema may shift *(currently embedded in § Current state)*
- Anti-patterns referenced may break *(if you remove a hygiene rule, anti-patterns 1, 2, 5, 6, 7 may stop applying)*

Treat this template like an interface. Version any breaking changes and migrate the delegate's existing module folders explicitly via a `migrate-module-claude-md` skill *(not yet built — only needed when we ship a v2 template)*.
